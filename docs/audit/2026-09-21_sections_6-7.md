## Highest-value gaps

1. **HITL escalation ladder (§6.5) — MISSING, size M.** The only thing standing between a P1 alert and nobody seeing it is a human noticing a card. Every other gate in this system is a refusal; this is the one that makes refusal safe. Needs `hitl.escalation` YAML, a `HITL_NUDGE` outbox kind with its own idempotency key, a deterministic `hitl_nudge` template and the `hitl.escalated` event. Nothing else in the build depends on a third party.

2. **Webhook hardening + `delivery_receipts` writer (§7.9.5, §6.6) — MISSING, size M.** The table, the status vocabulary and the provider-id column all exist and are unit-tested with hand-inserted rows; nothing writes them. Until the webhook half lands, "SENT" is the last thing the system can ever say about a message, and the replay/rate-limit/body-cap controls §7.9.5 calls a gap-closer are still a gap.

3. **Contracts production guard (§7.0.5, §7.8.6) — PARTIAL, size S.** `api/routers/complaints.py` has the guard; `api/routers/contracts.py` does not, and §7.8.6 names contracts explicitly. Confidential MSP contract text is served unauthenticated if `NOC_ENV=production` is ever set with `AUTH_DISABLED=true`. This is four lines copied from the complaints router.

4. **`validate_content(alert)` + the invented-cause check (§6.1) — MISSING, size S.** The per-channel validators already check the four required facts; what is missing is the envelope-level gate and the "no cause the incident does not evidence" rule. It costs little now and must exist *before* anything passes `ai_content` — and the `ai_content` seam is already open and tested.

5. **PIR LLM-draft sink (§7.7.3) — PARTIAL, size S.** `docs/PHASE4.md` §2 says it plainly: `PIR_ENABLED` + `LLM_ENABLED` today buys an audited, budgeted, recorded model call whose output nobody receives. One function in `services/pir.py`, under the blameless validator and a DRAFT/IN_REVIEW status guard.

6. **`PirsPage` + the Incident Workspace stop-clock / countdown controls (§7.10) — MISSING, size M.** Three complete, tested backend lanes (PIR, stop clocks, regulatory countdown) have no screen. A regulatory 24-hour countdown that exists only as JSON is not an operational control.

7. **`EMAIL_DAILY_CAP`, ≤100-recipient batching and the `send_email` signature change (§7.9.1) — MISSING, size S.** A free Gmail account earns a 24-hour suspension at 500 messages; the storm demo is well under, a real shift is not. The signature change is also a prerequisite for the `List-Unsubscribe` and iMIP headers the renderer already computes as hints.

8. **`OperatorConfig` fields for `weather`, `maintenance`, `capacity`, `memory`, `regulatory`, `scorecards` (§7.3.1, §7.5.1, §7.6.1, §7.11.3) — MISSING, size S.** Six lanes read `cfg.<block>` defensively and silently fall back to code defaults because pydantic's `extra="ignore"` drops the YAML. Every tuning knob the spec describes as "YAML, never code" is currently code-only. This is one field per block plus the YAML, and it unblocks the threshold-tuning the weather and capacity lanes were designed for.
